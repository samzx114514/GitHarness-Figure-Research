# 渲染与科学语义检查记录

检查方式：每次重新生成 3000 px PNG 与 1063 px 预览，逐张查看预览，再将六张拼成 contact sheet 对照整体构图。这里记录**实际发现和修正**，不把自动脚本当成视觉审查。

1. **初次渲染。** 第 03、04、06 张的纵向训练模块/紫箭头靠近或越过底缘；01/02 的训练回线从奖励文字附近发出而非 GRPO；03/04/05 的失败灰线从 v7 附近出发，可能误示“提交后失败”；01/06 把 candidate 宏观标记置于隔离边界外。
2. **路径与边界修正。** 将紫回线起点移到 Harness RL / GRPO 并回到同一 Git Agent；压缩纵向奖励到画布内；把灰失败线从**临时结果**引出。01/06 的隔离线只覆盖临时工作，v7 留在边界外。删去可能像“绕过执行”的橙色 v4→v7 捷径，以 Router、fork、工作更新和绿色提交构成可追踪主路。
3. **纸宽审查。** 放大主标签与版本号的字体；把 01/03/06 的 Task-Native Update 标签移离隔离标题及状态文字；04 的输入蓝带改为细小箭头而非过大箭头尖；05 的奖励回线回到同一策略。再检查时，01/06 的候选宏观标记仍会形成橙色直达提交的歧义，因此移除标记，保留边界、实际工作变化与绿色结果路径。将 04 的 fork 字移开路由字，将 05 的反馈字移开 Previous HEAD。六张都实看了 1063 px 预览，检查了旧 W4 与候选边界、唯一 v7、旧 HEAD v6、紫线终点、灰线起点。

**当前可见限制。** 一些淡灰的非激活标签（REUSE、Fresh Solve、Frozen）在屏幕模拟中需放大后读；它们不是第一眼主命题。候选 01 的局部展开仍有上下层感觉，候选 05 的策略中心较密，候选 06 的竖向读序有解释成本；这些是供下一轮选择方向时比较的设计取舍，不应被当作最终版已解决。没有实体打印、眼动或真实评审用户测试。
